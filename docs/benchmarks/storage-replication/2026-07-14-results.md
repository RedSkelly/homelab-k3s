# East-West Storage Replication Benchmark: 2026-07-14

## Summary

Six runs on 2026-07-14. Each finding is stated once here and detailed in the table cited.

1. **Longhorn does not replicate over VLAN 20.** The dedicated storage VLAN is configured, cabled,
   and running at line rate, but carries zero Longhorn traffic. Replication rides VLAN 10 via the
   flannel VXLAN overlay. This was measured, not inferred: see
   [Replication Path Verification](#replication-path-verification). It corrects the 2026-04-29
   results file, which stated traffic was "expected to use VLAN 20 based on Longhorn's storage
   network configuration". No such configuration exists: Longhorn's `storage-network` setting is
   empty (`value: ""`), and has been since install.
2. **Longhorn's sequential ceiling is ~233 MB/s write / ~402 MB/s read**, about 2x what the
   default iodepth=1 tests reported. See
   [Table 3](#table-3-sequential-queue-depth-scaling-second-run).
3. **The write ceiling was CPU-bound, not disk or network.** It survives removal of all
   file-sharing artifacts ([Table 4](#table-4-is-the-233-mbs-ceiling-real-third-run)), and during a
   saturated write the engine node sat at ~90% CPU on 2 vCPU with `%iowait` of 1.04%. Longhorn's
   own iSCSI data path consumed ~73% of the node, and `tgtd` showed 44.5% runqueue wait
   ([Table 4b](#table-4b-cpu-profile-of-the-engine-node-under-saturated-write)). The lever is
   vCPU, not faster disks or a VLAN 20 migration.
4. **Tested by intervention and upheld.** wk-01 was resized 2 → 4 vCPU and the identical tests
   re-run: write throughput rose from ~225 to ~371 MB/s (+65%). The "233 MB/s Longhorn ceiling"
   was the throughput of Longhorn's data path on 2 cores, not a property of Longhorn. This is the
   one causal result in this document; the rest is correlation. See
   [Table 5](#table-5-the-vcpu-intervention-2-vcpu-vs-4-vcpu-fourth-run).
5. **3 vCPU is the chosen size, and the bottleneck has moved off CPU.** A 2/3/4 sweep with CPU
   capture on all three workers shows 3 vCPU delivers 87% of the 4-vCPU throughput at one fifth
   the `%steal` (0.51% vs 2.69%); the 4th vCPU buys +14% and oversubscribes pve1's 6 cores, taxing
   an etcd node. The replica nodes were never CPU-bound: wk-02/wk-03 sit at ~35% idle with ~29%
   `%iowait`, so more vCPU there would do nothing. At 3 vCPU the engine node is no longer
   CPU-starved (`tgtd` `%wait` 44.5% → 0.00%), and the next constraint is SATA SSD write latency
   on the replicas, which no VM setting fixes. See
   [Table 6](#table-6-vcpu-sweep-and-all-worker-cpu-profile-fifth-run).
6. **The disk-bound claim survives a falsification test.** All three workers were raised to
   3 vCPU. Throughput moved +1.8% (325.0 → 330.9 MB/s), inside the noise band. The third core on
   each replica node became ~15 points of idle (35% → ~50%) while `%iowait` stayed ~27% and the
   `longhorn` replica process consumed the same ~61% of a core. Adding CPU to a disk-bound node
   produces idle, not throughput. Current state is uniform 3 vCPU, chosen because engine placement
   is dynamic and any worker may become the engine node. See
   [Table 7](#table-7-all-workers-at-3-vcpu-a-falsification-test-sixth-run).

## Table 3: Sequential Queue-Depth Scaling (second run)

The iodepth=1 sequential numbers above are latency-bound and understate Longhorn by ~2x.
Re-ran sequential read/write at higher concurrency to find the actual ceiling. Same pod
placement (k3s-wk-01), same 2Gi PVC, 3 replicas, `error=0` on all runs.

**Sequential write**

| Config | Bandwidth (MB/s) | IOPS | Avg Latency (us) | P99 Latency (us) |
|---|:-:|:-:|:-:|:-:|
| iodepth=1, numjobs=1 (baseline) | 118.2 | 118 | 8,452 | 12,517 |
| iodepth=16, numjobs=1 | 233.0 | 233 | 68,572 | 162,529 |
| iodepth=16, numjobs=4 | 233.0 | 233 | 270,087 | 476,054 |

**Sequential read**

| Config | Bandwidth (MB/s) | IOPS | Avg Latency (us) | P99 Latency (us) |
|---|:-:|:-:|:-:|:-:|
| iodepth=1, numjobs=1 (baseline) | 152.7 | 153 | 6,541 | 9,241 |
| iodepth=16, numjobs=1 | 336.6 | 337 | 47,470 | 235,930 |
| iodepth=16, numjobs=4 | 401.7 | 402 | 158,878 | 354,419 |

### What this shows

Writes hit a ceiling at 233 MB/s. Going from 16 to 64 outstanding I/Os (numjobs 1→4) produced no
extra throughput (233.04 vs 233.00 MB/s) while average latency rose 3.9x (68.6ms → 270ms). That
is queue saturation: the service rate is fixed, so deeper queueing only adds wait time. Little's
Law confirms the pipe is full at both depths:

- `16 outstanding x 1MB / 68.57ms  = 233 MB/s`
- `64 outstanding x 1MB / 270.09ms = 237 MB/s`

Reads scale further, to ~402 MB/s, still gaining 19% from the extra jobs. Reads have no
replication fan-out to pay for and are served without a 3-way commit.

So roughly half the sequential gap in the baseline was pipeline starvation and half is real.
Longhorn's sequential ceiling on this cluster is ~233 MB/s write / ~402 MB/s read, not 118 / 153.

> **Follow-up (third run):** the `numjobs=4` rows above shared a single `--filename`, so
> those jobs wrote overlapping offsets, raising the possibility that the write ceiling was
> a contention artifact rather than a real limit.
> [Table 4](#table-4-is-the-233-mbs-ceiling-real-third-run) tested this directly with one file
> per job and the ceiling held (224.2 vs 226.2 MB/s control). These numbers stand as written.

## Table 4: Is the 233 MB/s Ceiling Real? (third run)

Table 3's `numjobs=4` runs shared one `--filename`, so the four jobs wrote overlapping
regions of the same file. That left an alternative explanation: the ceiling might
have been an artifact of write contention on shared offsets rather than a real limit.

**Design.** Both variants run in the same session, same pod, same 2Gi PVC, same pinned
node, so file-sharing is the only variable. `size=400M` (4 separate files = 1.6G, fits the
PVC) and `--time_based --runtime=30` for a steady-state window. The shared-file control
re-runs Table 3's configuration at the new size, so the size change cannot confound the
comparison. Pod was pinned to wk-01 via `nodeSelector`, and the engine was confirmed on
wk-01 before running.

| Run | Files | Bandwidth (MB/s) | Avg Latency (us) |
|---|---|:-:|:-:|
| A, control (shared `--filename`) | 1 file, overlapping offsets | 226.2 | 282,905 |
| B, test (`--directory=/data`) | 4 files, no overlap | 224.2 | 285,259 |

Both `error=0`. Run B created `seq-write.0.0` … `seq-write.3.0`, 400M each, verified on
disk, so the jobs wrote distinct files.

The ceiling is real. Removing all offset overlap changed throughput by −0.9% (224.2 vs
226.2), inside run-to-run noise. Both variants also land within ~3% of Table 3's 233 MB/s, so
Table 3's finding stands and needs no rewrite.

### What the CPU data establishes

- **Disk is not the bottleneck.** `%iowait` of 1.04% is the direct measurement that earlier runs
  could only infer from headroom arithmetic.
- **The node is out of CPU.** ~90% utilised, 2-5% idle at steady state, both cores even.
- **The cost is Longhorn's own data path.** Engine + `tgtd` + replica + iSCSI kworkers
  ≈ 145% of 200% available, roughly 73% of the node and ~1.45 of its 2 cores.
- **`tgtd` is CPU-starved:** 44.5% `%wait` is time spent on the runqueue waiting for a core,
  not doing work. On a node with spare CPU this would be ~0.
- **Only 25% of the load is userspace.** `%sys` 45.8% + `%soft` 18.1% = ~64% kernel: the
  iSCSI block path and network stack, not application code.

**Calibration:** ~90% is not 100%, so this is evidence for CPU-bound rather than proof. The
decisive test is to add vCPU to a worker and re-run: if the ceiling moves, CPU was the limit.

> **Resolved (fourth run):** that test was run. wk-01 went 2 → 4 vCPU and write throughput
> rose ~65% (225 → 371 MB/s). CPU was the binding constraint. See
> [Table 5](#table-5-the-vcpu-intervention-2-vcpu-vs-4-vcpu-fourth-run).

**Confound worth recording:** `prometheus` consumed ~11% of a core on wk-01 throughout. This is
real background load from kube-prometheus-stack, on the exact node under test and on a node
that had no CPU to spare. It is not large enough to explain a 233 MB/s ceiling, but every
figure here was measured with it running.

## Table 5: The vCPU Intervention, 2 vCPU vs 4 vCPU (fourth run)

Table 4b showed the engine node at ~90% CPU and argued CPU was the constraint, while noting
that ~90% is evidence, not proof, and that the decisive test is to add vCPU and re-run.
k3s-wk-01 was resized from 2 → 4 vCPU and the identical tests re-run. wk-02 and wk-03
were left at 2 vCPU.

This is the only causal claim in this document. Everything else is correlation across
observations; this is a single-variable intervention with the outcome measured either side.

| Run (numjobs=4, iodepth=16, bs=1M, 30s) | 2 vCPU | 4 vCPU | Change |
|---|:-:|:-:|:-:|
| A, shared `--filename` | 226.2 MB/s | 371.8 MB/s | +64.4% |
| B, separate files (`--directory`) | 224.2 MB/s | 371.0 MB/s | +65.5% |

All runs `error=0`; volume `healthy` throughout; pod pinned to wk-01 with engine placement
verified before each run.

CPU was the binding constraint on write throughput. Doubling vCPU on the engine node
lifted the write ceiling ~65%, an effect ~20x larger than the ~1-3% run-to-run noise seen
across every other repeat in this document. The 233 MB/s ceiling was the throughput of
Longhorn's data path on 2 cores, not a property of Longhorn.

### CPU profile at 4 vCPU (mpstat, run B, 30s)

| %usr | %sys | %soft | %iowait | %steal | %idle |
|:-:|:-:|:-:|:-:|:-:|:-:|
| 18.51 | 40.56 | 18.51 | 6.14 | 2.69 | 13.59 |

| Process | %CPU @ 2 vCPU | %CPU @ 4 vCPU | %wait @ 4 vCPU |
|---|:-:|:-:|:-:|
| `longhorn` (engine) | 56.1 | 97.8 | 0.0 |
| `tgtd` | 32.6 | 77.2 | 21.4 (was 44.5) |
| `longhorn` (replica) | 28.9 | 43.1 | 0.6 |
| `kworker` flush/writeback/iscsi | ~28 | ~56 | |
| `prometheus` | 11.0 | 13.9 | |

### Where the bottleneck moved to

Relieving CPU did not remove the limit; it moved it. Three signals point in different
directions:

1. **The engine thread is now at ~98% of one core** (up from 56%). Longhorn v1's engine is
   single-threaded, so it is approaching a per-thread ceiling. More vCPU cannot lift this;
   only more volumes (more engines) or a Longhorn v2 data path could.
2. **`%iowait` rose from 1.04% → 6.14%.** At 371 MB/s each replica writes ~74% of a SATA
   III SSD's ~500 MB/s assumed ceiling. The disks were irrelevant at 233 MB/s; they are
   becoming relevant now.
3. **`%steal` rose from 0.17% → 2.69%**, a side effect of the change. wk-01 (now 4 vCPU)
   shares pve1 with k3s-cp-01 (4 vCPU) on an i5-8500T with 6 physical cores. 8 vCPU on 6
   cores is ~1.33x oversubscribed, and the hypervisor is now stealing measurable time. This
   cost is paid by an etcd control-plane node on the same host. See follow-ups.

**Why +65% and not +100%?** Two candidates, unseparated: (a) the engine's single-thread
ceiling is close, and (b) wk-02 and wk-03 are still 2 vCPU and must each receive and
write the full 371 MB/s stream, so the remote replicas may now be the limit. This run
captured CPU only on wk-01, so this is not settled.

## Table 6: vCPU Sweep and All-Worker CPU Profile (fifth run)

Table 5 left two things open: whether 3 vCPU keeps most of the gain while avoiding the pve1
`%steal` penalty, and whether wk-02/wk-03 at 2 vCPU were themselves limiting throughput.
wk-01 was resized 4 → 3 vCPU and the identical tests re-run, this time capturing
`mpstat`/`pidstat` on all three workers concurrently.

### The vCPU sweep (engine node = wk-01; wk-02/wk-03 held at 2 vCPU throughout)

| wk-01 vCPU | Write A (shared) | Write B (separate) | %steal | %idle | MB/s per vCPU |
|:-:|:-:|:-:|:-:|:-:|:-:|
| 2 | 226.2 | 224.2 | 0.17 | 9.73 | 113 |
| 3 | 324.4 | 325.6 | 0.51 | 14.08 | 108 |
| 4 | 371.8 | 371.0 | 2.69 | 13.59 | 93 |

Scaling is sharply diminishing: 2→3 vCPU = +44%, 3→4 vCPU = +14%.

3 vCPU is the knee of the curve. It delivers 87% of the 4-vCPU throughput at one fifth the
steal (0.51% vs 2.69%), because 3+4=7 vCPU on pve1's 6 cores is barely oversubscribed where
4+4=8 is meaningfully so. The 4th vCPU buys +14% throughput and a 5x steal increase on a host
shared with an etcd control-plane node. On this hardware, 3 vCPU is the recommendation.

At 3 vCPU the engine node is also no longer CPU-starved: `tgtd` `%wait` is 0.00%, down
from 44.5% at 2 vCPU.

### All three workers under load (run B, 3 vCPU engine node)

| Node | Role | vCPU | %usr | %sys | %soft | %iowait | %steal | %idle |
|---|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| wk-01 | engine + replica | 3 | 20.80 | 43.27 | 18.80 | 2.55 | 0.51 | 14.08 |
| wk-02 | replica | 2 | 12.29 | 13.01 | 10.75 | 28.86 | 0.19 | 34.89 |
| wk-03 | replica | 2 | 12.74 | 11.98 | 10.93 | 29.00 | 0.17 | 35.18 |

Top processes: wk-01 runs `longhorn` (engine) 79.3%, `tgtd` 53.3%, `longhorn` (replica)
35.9%, flush kworker 23.8%, `prometheus` 13.0%, all with `%wait` 0.00. wk-02 and wk-03 each
run a single `longhorn` replica process at ~61% of one core, plus `k3s-agent` at ~4%.

### Were the replica nodes the limit?

No, and this reverses the premise. The remote replicas are not CPU-bound; they are
disk-bound. wk-02 and wk-03 sit at ~35% idle with only ~37% of their CPU used, while showing
~29% `%iowait`. They have CPU to spare and are waiting on their SATA SSDs.

Giving wk-02/wk-03 more vCPU would not help, which is the opposite of what the previous
run's follow-ups proposed testing ("re-run with all three workers at 4 vCPU"). The all-worker
capture answered it directly, for the cost of two extra `mpstat` invocations:

- The engine node is a CPU problem (~14% idle, 3 processes + kworkers competing).
- The replica nodes are a disk problem (~35% idle, ~29% iowait, one process each).

They are different bottlenecks on different nodes, so a uniform "give every worker more vCPU"
change would fix one and waste resources on the other.

**So why +65% and not +100% in Table 5?** Table 5 offered two candidates; this run
eliminates one. It is not wk-02/wk-03 being CPU-starved, since they never were. What remains
is the engine's single-thread ceiling plus replica disk latency, visible at ~29% iowait. At
325 MB/s each replica writes ~65% of a SATA III SSD's ~500 MB/s assumed ceiling, and every
write must commit on all three before ack, so remote disk wait feeds back into the engine's
throughput.

The bottleneck has moved off CPU. At 2 vCPU the answer was "add cores". At 3 vCPU the engine
node is no longer starved, the replica nodes are idle but waiting, and the next constraint is
SATA SSD write latency on the replicas, which no VM setting fixes.

## Table 7: All Workers at 3 vCPU, a Falsification Test (sixth run)

Table 6 made a falsifiable prediction: wk-02/wk-03 are disk-bound with CPU to spare, so
giving them a third vCPU should produce no meaningful throughput gain. All three workers
were resized to 3 vCPU and the identical tests re-run. If throughput had jumped, Table 6's
claim was wrong.

### Result: the prediction holds

| Config (engine always on wk-01) | Write A | Write B | Mean | vs previous |
|---|:-:|:-:|:-:|:-:|
| wk-01 @ 3 vCPU, wk-02/03 @ 2 vCPU (Table 6) | 324.4 | 325.6 | 325.0 | |
| All three @ 3 vCPU | 332.9 | 328.9 | 330.9 | +1.8% |

+1.8% is inside the ~1-3% run-to-run noise band seen across every repeat in this
document. Six extra vCPU-equivalents of replica-side capacity bought nothing measurable.

### Why: the extra core became idle, not throughput

| Node | Role | %iowait @ 2 vCPU | %iowait @ 3 vCPU | %idle @ 2 vCPU | %idle @ 3 vCPU | `longhorn` proc %CPU |
|---|---|:-:|:-:|:-:|:-:|:-:|
| wk-02 | replica | 28.86 | 26.78 | 34.89 | 49.75 | ~61 → ~60 |
| wk-03 | replica | 29.00 | 27.62 | 35.18 | 49.46 | ~61 → ~61 |

On the replica nodes the third core:

- added ~15 points of idle (35% → ~50%),
- left `%iowait` essentially unchanged (~29% → ~27%), still waiting on disk,
- left the `longhorn` replica process consuming the same absolute CPU (~61% of one core,
  before and after).

The replica process was never short of CPU, so a third core had nothing to do. Adding CPU
to a disk-bound node produces idle, not throughput.

### Engine node: unchanged, as expected

| Node | %usr | %sys | %soft | %iowait | %steal | %idle |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| wk-01 (3 vCPU, engine) | 20.87 | 43.65 | 18.33 | 2.99 | 0.56 | 13.60 |

Statistically identical to Table 6's wk-01 row (13.60% vs 14.08% idle, 0.56% vs 0.51%
steal). Engine 78.4%, `tgtd` 53.7%, replica 36.4%, all at `%wait` 0.00. Nothing about the
engine node was changed, and nothing about it changed.

### What this costs, and the sizing decision it forces

Every pve host is now 7 vCPU (CP 4 + worker 3) on 6 physical cores. `%steal` on the
replica nodes rose slightly (wk-02 0.19% → 0.30%, wk-03 0.17% → 0.27%), and it is
now being paid on all three hosts, each running an etcd control-plane node, in exchange
for ~15 points of idle CPU on the workers.

The measurement says the third vCPU is unused on a replica-only node. It does not say
"revert to 2 vCPU":

- **Engine placement is dynamic.** It follows the attaching pod, so any worker can become
  the engine node after a reschedule, drain, or reboot. A 3/2/2 layout is only optimal while
  engines happen to live on wk-01, which nothing enforces.
- **A real cluster runs many volumes**, and engines spread across nodes. Each worker would
  then be an engine for some volumes and a replica for others, and would want the third core.
- **Uniform 3 vCPU is therefore defensible** as "any node may be an engine", at a measured
  cost of ~0.3% steal and idle CPU on nodes not currently hosting an engine.

Recommendation: keep uniform 3 vCPU, on the grounds that engine placement is not pinned
and uniformity is worth more than the ~0.3% steal. The single-volume benchmark makes the
third core look unused on wk-02/wk-03; a multi-volume workload (the "benchmark multiple
concurrent volumes" item under [Recommended Follow-ups](#recommended-follow-ups)) is the
case where it would be used. Revisit if that measurement shows otherwise.

## Bottleneck Analysis (2-vCPU state)

> Superseded by [Table 5](#table-5-the-vcpu-intervention-2-vcpu-vs-4-vcpu-fourth-run). The
> ~233 MB/s ceiling this section is built on was a 2-vCPU ceiling, not a Longhorn one. At
> 4 vCPU the same test yields ~371 MB/s, ~74% of the SATA III ceiling, so the "2.1x cost of
> replication" framing below is wrong: most of that gap was CPU starvation, not replication
> overhead. The per-node arithmetic remains correct as a description of the 2-vCPU state.

Using the measured ceilings from Table 3 (not the latency-bound iodepth=1 figures):

| Layer | Throughput | Notes |
|---|:-:|---|
| VLAN 10 (actual replication path) | ~9.51 Gbps (~1,189 MB/s) | Near line rate |
| VLAN 20 (idle, unused by Longhorn) | ~9.58 Gbps (~1,197 MB/s) | Carrying no storage traffic |
| SATA SSD (assumed) | ~500 MB/s | Typical SATA III ceiling, not measured here |
| Longhorn seq write (ceiling) | 233.0 MB/s | 2.1x below SATA SSD max |
| Longhorn seq read (ceiling) | 401.7 MB/s | 1.2x below SATA SSD max |

Neither the network nor VLAN choice is the bottleneck. Reads are effectively disk-bound at
~80% of a SATA III SSD's assumed ceiling. Writes were bound by CPU on the engine node.

### Per-node load at the 233 MB/s write ceiling

wk-01 held the engine and one of the three replicas, so it does two jobs at once and is the
node that would hit a limit first:

| Node | Role | Local disk write | Network |
|---|---|:-:|:-:|
| k3s-wk-01 | engine + replica | 233 MB/s | ~466 MB/s egress (233 to each of 2 remotes) |
| k3s-wk-02 | replica | 233 MB/s | ~233 MB/s ingress |
| k3s-wk-03 | replica | 233 MB/s | ~233 MB/s ingress |

Every replica writes the full stream, so all three nodes carry the same 233 MB/s of disk
write. wk-01 does that simultaneously with ~466 MB/s of network egress, double the network
load of either remote, because the engine fans each write out to both remotes itself. The fio
pod also ran on wk-01, so the incoming write stream reaches the engine locally rather than
over the network.

wk-01's ~466 MB/s egress is ~39% of the ~1,189 MB/s fabric, so the network was never close to
saturated even at the busiest node. Table 4b then measured `%iowait` at 1.04% and CPU at ~90%,
which settles the question directly rather than by elimination: the engine's cost is paid in
CPU, and the node runs out of CPU first. The single-threaded userspace iSCSI data path is what
burns the cores.

**Practical implication (updated after the fourth run):** a single volume's write ceiling is
set by CPU on the engine node: ~225 MB/s at 2 vCPU, ~371 MB/s at 4 vCPU. It is not a
fixed Longhorn constant. Spreading load across multiple volumes still helps, since each
volume gets its own engine and separate volumes place engines on different nodes, spreading
the concentrated egress that the engine node carries. But the first lever is engine-node
vCPU, subject to the pve1 oversubscription caveat under
[Recommended Follow-ups](#recommended-follow-ups). Table 6 settles the sizing question at
3 vCPU.

| Metric | 2026-04-29 | 2026-07-14 | Change |
|---|:-:|:-:|:-:|

| iperf3 retransmits | 55-68K | ~30K | ~2x fewer |
| Seq write | 94.3 MB/s | 118.2 MB/s | +25% |
| Seq read | 132.2 MB/s | 152.7 MB/s | +16% |
| Random write 4K | 11.3 MB/s | 12.0 MB/s | +6% |
| Random read 4K | 23.0 MB/s | 23.4 MB/s | +2% |

One known configuration change separates these runs: MTU went from 1500 to 9000 on VLAN 10
and VLAN 20 (jumbo frames enabled after the April run, acting on that run's own follow-up
recommendation). This run is therefore the re-benchmark April asked for.

What the comparison supports, stated carefully:

- Retransmits roughly halved (55-68K → ~30K) and sequential throughput rose 16-25%,
  while 4K random stayed flat (+2-6%, within noise). The direction is what a larger MTU
  would predict: large sequential transfers benefit from ~6x fewer packets, interrupts and
  ACKs for the same bytes, whereas 4K I/Os never filled even a 1500-byte frame and are
  bound by per-I/O latency and the 3-replica commit, neither of which frame size touches.
- That makes the result weakly consistent with April's MTU hypothesis. It is not
  confirmation. This is one uncontrolled run per configuration, three months apart, with
  background load, kernel state, and cluster activity all unheld. MTU is the only known
  delta, not provably the only delta.
- What the data does establish: retransmits persist at ~2.3% of packets with jumbo
  frames enabled. MTU was not the sole cause of the retransmit anomaly, and whatever
  else contributes was not addressed by the MTU change.

Treat the percentages as indicative, not precise. Isolating the MTU contribution would need
A/B runs at both MTUs in the same session.

This table compares like with like: both runs used iodepth=1 sequential. Neither
column reflects Longhorn's ceiling, which Table 3 gives. April has no iodepth=16
equivalent to compare against.

## Anomalies Flagged

- **VLAN 20 carries no storage traffic.** A dedicated 10GbE storage fabric is provisioned and
  idle while storage traffic contends with cluster, API, and pod traffic on VLAN 10.
- **Retransmits persist at ~2.3% of packets with jumbo frames enabled** (~30K over 10s at
  9.5 Gbps, down from 55-68K in April). The firm conclusion is narrow: MTU was not the
  sole cause. Enabling jumbo frames coincided with roughly half the retransmits going
  away, but half remain. April's other hypothesis, undersized socket buffers
  (`net.core.rmem_max` / `wmem_max`) for 10GbE, remains untested and is one candidate; TCP
  window growth under 4 parallel streams is another, and would be benign. Throughput sits at
  line rate regardless, so this is not currently costing anything. Low priority.
- **P99 random-write latency of 117ms** is high. Expected for 4K sync-replicated writes to
  SATA SSDs, but worth knowing before running latency-sensitive workloads (e.g. a database)
  on this cluster.

## Method Notes / Repeatability

Six runs on 2026-07-14: the main run (iperf3 + 4 fio tests + replication path
verification), a second for Table 3 (sequential at iodepth=16), a third for Tables 4/4b
(file-sharing control + CPU profile), a fourth for Table 5 (same tests at 4 vCPU), a fifth
for Table 6 (3 vCPU + all-worker CPU capture), and a sixth for Table 7 (all workers at
3 vCPU). Each used a fresh 2Gi PVC. The first two landed on k3s-wk-01 by chance; runs three
through six pinned the pod to wk-01 via `nodeSelector` and verified engine placement before
measuring, so all six are comparable.

- **Cluster topology changed repeatedly mid-document.** Worker vCPU by run:

  | Runs | wk-01 | wk-02 | wk-03 | Tables |
  |---|:-:|:-:|:-:|---|
  | 1-3 | 2 | 2 | 2 | 1, 2, 3, 4, 4b |
  | 4 | 4 | 2 | 2 | 5 |
  | 5 | 3 | 2 | 2 | 6 |
  | 6 (current) | 3 | 3 | 3 | 7 |

  Tables 1-4b describe a uniform 2-vCPU worker cluster that no longer exists and will not
  reproduce. Table 6 is the one place the 2/3/4 sweep is compared like-for-like (engine node
  only). CLAUDE.md documented workers as 2 vCPU / 12GB when this was written; it was
  corrected to 3 vCPU on 2026-07-27.
- The vCPU resize rebooted wk-01, which left `pvc-ede5c1ba` degraded and rebuilding.
  The fourth run was held until rebuild completed and all volumes reported `healthy`, since
  rebuild traffic competes for exactly the CPU/disk/network under measurement.
- The fio pod's own limit stayed at `cpu: "2"` across all runs, including the 4-vCPU run,
  so the pod is identical throughout. This does not confound Table 5: the engine, `tgtd`
  and replica processes run outside the pod (host / instance-manager), which is where the
  extra cores were consumed.
- iperf3 was absent on all 3 workers beforehand, installed for the main run, and removed
  afterward (`apt-get remove -y iperf3 && apt-get autoremove -y`); removal verified, and
  re-verified still absent after the follow-up run.
- Test namespace `storage-bench`, PVC, and pod all deleted after both runs; verified no
  leftover Longhorn volume, no orphaned replicas, and all 3 pre-existing volumes still
  `attached`/`healthy`. Longhorn takes ~10s to garbage-collect the volume after PVC
  deletion, so an immediate check will show a false leftover.
- Table 3 caveat (resolved): with `numjobs=4` sharing one `--filename`, the jobs write
  overlapping regions of the same file rather than distinct ranges. Table 4 re-tested this
  with `--directory` (one file per job) and found no difference.
- `sysstat` (`mpstat`/`pidstat`) was already installed on wk-01, so no host package was
  added to collect Table 4b. Only the capture files under `/tmp` were written, and they
  were removed afterward; both samplers confirmed stopped.
- Table 4 sizing: `--directory` with `numjobs=4 --size=1G` needs 4G of separate files and
  will ENOSPC on a 2Gi PVC. Dropped to `size=400M` (1.6G total) and re-ran the shared-file
  control at the same size rather than enlarging the PVC, keeping file-sharing as the only
  changed variable.
- No Longhorn settings, StorageClasses, or existing volumes were modified. Nothing was
  committed or pushed.
- Two gotchas worth remembering: `pgrep -f "iperf3 -s"` self-matches the SSH command
  string (false positive; `pkill -f` on the same pattern kills its own session, use
  `-x`), and the workers are not resolvable by hostname from the Mac, so SSH needs IPs.
